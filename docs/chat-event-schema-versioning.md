# Chat Event schema versioning

Snapshot NDJSON rows and Raw Chat Event API rows are two representations of
the same Chat Event schema. Clients select that schema with
`X-Chat-Event-Schema-Version` on both read endpoints, and successful responses
echo the selected version in the same header.

## Version negotiation

- The current version is V5 and the downgrade floor is V4, so the supported
  interval is `[4, 5]`.
- A missing header temporarily selects the fixed legacy default V5. It must not
  start following future current-version bumps. Remove that default through
  #27194 after the ~2-day old app-client window and up-to-2-hour existing
  runner/sandbox window have both drained.
- A malformed version returns `400 CHAT_EVENT_SCHEMA_VERSION_INVALID`.
- A version below the downgrade floor returns
  `426 CHAT_EVENT_SCHEMA_VERSION_RETIRED` so the client can force an upgrade.
- A version newer than the API returns
  `409 CHAT_EVENT_SCHEMA_VERSION_AHEAD`.

Raw Events are read from the current database schema and projected through an
adjacent downgrade chain. The V5-to-V4 projection removes feedback `eventId`
and `range` fields. Every version in the supported interval must have a
complete adjacent downgrade path from the current version. Retire V4 through
#27194 after the same client windows drain and production no longer observes
explicit V4 reads.

## Snapshot storage and reads

The current API owns one canonical pointer per
`(chat_thread_id, archive_schema_version)`. During the expand release, the
previous API may still append historical rows for the same version; readers
choose the head and then the latest cursor deterministically. The version index
remains non-unique until that API and its rollback window have drained, when
#27174 deduplicates the rows and makes the index unique.

The pointer contains the immutable, content-addressed R2 object key and a
paired `{lastEventId, lastSeqId}` terminal cursor. `last_event_id` remains
physically nullable during the same window, with migration 0923 filling legacy
writes through a trigger. The legacy `is_head` column identifies the canonical
rollout row until the contraction is complete.

Current-version Snapshot reads persist a current-version pointer. Older
versions are normally generated by transiently downgrading the current object;
they do not create an older-version database pointer. A request cannot fall
back to a stored older pointer when the current pointer is unavailable.

## Snapshot upgrade invariant

Only the first Snapshot for a thread may bootstrap from Raw Events, and only
when those rows start at sequence 1. Once any Snapshot exists, every refresh or
schema upgrade must:

1. Download and validate the stored Snapshot object.
2. Run the adjacent Snapshot migration chain on that historical prefix.
3. Read only Raw Events after the stored paired cursor.
4. Append that tail, upload a new immutable object, then publish its database
   pointer with an exact compare-and-swap.

A missing object, invalid Snapshot, missing migration, or missing historical
prefix fails closed. It must never authorize a full Raw Event rebuild because
older Raw Events may already have been reclaimed.

Snapshot upgrade and Raw Event downgrade chains are intentionally separate.
V4 cannot upgrade losslessly to V5 because V4 discarded feedback location
information. Therefore this change must not be released until no thread relies
on a V4 head. Future Chat Event schema bumps must include every required
adjacent Snapshot migration before release; if an old version is not
migratable, all pointers relying on it must first converge to a migratable
version.

## Browser cache

The IndexedDB database version combines a cache-layout base version with the
requested Chat Event schema version. Any IndexedDB version change deletes and
recreates all Chat Event cache stores. The cache cursor stores the schema
version and paired event/sequence boundary, and row-plus-cursor writes are
atomic.

Raw Event retention and orphaned R2 object collection policy are outside this
change. The invariant above makes later Raw Event reclamation safe without
adding retention behavior here.
